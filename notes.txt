every function that works with the luau virtual machine requires you to pass a reference to the lua_State object, above you see it passed as 'L', thats how its defined in source code.
at its core lua_State represents a single thread of execution (a coroutine in the luau vm, scripting environment) in the luau vm.
whenever you call a c api function like lua_pushnumber(L, 10) or lua_pcall(L, ...), the lua_State* L parameter tells the VM which thread context, evaluation stack, and memory space you are

when creating a new lua_State struct object with luaL_newstate() it automatically creates the global_State struct object alongside the lua_State object and its thread.
all threads created via lua_newthread(L) (or coroutine.create() in luau vm scripting environment) point back to this single global_State struct, which owns the garbage collector, string table,
registry table and primitive metatables.
this is how it all works, when creating the lua_State with luaL_newstate(), the vm performs a single combined allocation in memory that creates both the root global_State and the primary
lua_State (the main thread).
global_State is allocated once, it owns all state that must persist across the entire application lifecycle (strings, memory allocators, global registry, and the garbage collector).
the main lua_State is created, its internal pointer L->global (dereference pointer to lua_State struct (L) and access the member variable named global inside it) is pointed directly at the newly
created global_State. global_State->mainthread is pointed back to this primary lua_State.
when lua_newthread(L) (or coroutine.create in a luau script) is called, Luau does not create a new global_State, instead it allocates a lightweight child lua_State.
it basically inherits the engine, the new child lua_State struct has its internal global pointer set to L->global (copying the address of the existing global_State).
what is isolated, it allocates its own execution stack array and call frame tracking buffer.
parent relationship, the new lua_State object is pushed onto the stack of the parent lua_State as a value of type LUA_TTHREAD.

The provided code implements a classic Windows API techniques known as Remote Thread Injection via LoadLibraryA. Because every process on Windows runs within its own isolated Virtual Address Space, one process cannot directly call functions or pass pointers to another process.
The injection routine bridges this isolation through six sequential kernel-level steps:
1. 	Acquiring Process Handle (OpenProcess)
C++:		HANDLE Proc = OpenProcess(CREATE_THREAD_ACCESS, FALSE, ProcessID);
Mechanism: The code calls OpenProcess to request access to the target process kernel object (EPROCESS). It requests specific access flags defined by CREATE_THREAD_ACCESS:
PROCESS_CREATE_THREAD: Permission to spawn remote threads.
PROCESS_VM_OPERATION: Permission to modify the virtual address space (needed for allocation).
PROCESS_VM_WRITE & PROCESS_VM_READ: Permission to write and read target memory.
OS Behavior: The NT Kernel checks Security Descriptors and Integrity Levels (e.g., non-admin processes cannot open handle access to administrative or system processes). If authorized, the OS returns a HANDLE mapped into the caller’s handle table.
2. Resolving the Loader Function Pointer (GetProcAddress)
C++:		LoadLibAddy = (LPVOID)GetProcAddress(GetModuleHandle("kernel32.dll"), "LoadLibraryA");
Mechanism: The host process looks up the memory address of the LoadLibraryA function inside its own loaded instance of kernel32.dll.
Why this works remotely: Core system DLLs (kernel32.dll, ntdll.dll) are loaded at identical virtual base addresses across every process during a single Windows boot session (due to how Address Space Layout Randomization, or ASLR, assigns system module bases on boot). Therefore, the memory address of LoadLibraryA in the host process is identical to its address in the target process.
3. 	Remote Memory Allocation (VirtualAllocEx)
C++:		RemoteString = (LPVOID)VirtualAllocEx(Proc, NULL, strlen(DLL_PATH) + 1, MEM_COMMIT, PAGE_READWRITE);
Mechanism: Because memory addresses are local to each process's Virtual Memory Manager, passing a local string pointer to another process would cause an invalid memory access (segfault/crash).
OS Behavior: VirtualAllocEx instructs the kernel to allocate and commit physical page frames mapped to the target process’s Virtual Address Descriptor (VAD) tree.
MEM_COMMIT: Allocates actual physical memory/paging space.
PAGE_READWRITE: Sets page protection flags to allow writing the path string.
4. 	Writing Across Process Memory Boundaries (WriteProcessMemory)
C++:		WriteProcessMemory(Proc, RemoteString, (LPVOID)DLL_PATH, strlen(DLL_PATH)+1, NULL);
Mechanism: Copies the null-terminated ANSI string containing the DLL file path from the local host process buffer (DLL_PATH) into the newly allocated remote address (RemoteString).
OS Behavior: The OS kernel handles the memory transfer across address spaces using internal page-mapping routines (such as MmCopyVirtualMemory), writing the bytes directly into the target process's committed RAM pages.
5. 	Spawning Remote Execution (CreateRemoteThread)
C++:		CreateRemoteThread(Proc, NULL, NULL, (LPTHREAD_START_ROUTINE)LoadLibAddy, RemoteString, NULL, NULL);
Mechanism: CreateRemoteThread creates a new execution thread (ETHREAD) inside the target process.
Function Signature Alignment:
A standard Win32 thread entry point requires: DWORD WINAPI ThreadProc(LPVOID lpParameter)
LoadLibraryA requires: HMODULE WINAPI LoadLibraryA(LPCSTR lpLibFileName)
Because both use the standard calling convention (__stdcall on x86, standard register passing on x64) and accept a single pointer parameter, LoadLibraryA can be passed directly as the thread entry function pointer, with RemoteString passed as its single parameter.
Target OS Loader Action: When the new thread executes inside the target process, it immediately calls LoadLibraryA(RemoteString). This triggers the Windows PE loader (ntdll!LdrLoadDll), which:
Opens and reads the DLL file from disk.
Maps the PE sections (.text, .data, .rdata) into the target's address space.
Resolves necessary import tables.
Calls the DLL's entry point (DllMain) with DLL_PROCESS_ATTACH.
6. 	Resource Cleanup (CloseHandle)
C++:		CloseHandle(Proc);
Mechanism: Decrements the Kernel Object Reference Count for the target process handle. The memory allocated in the target process remains committed while the thread runs.

ive been using the words decleration and definition a bit loosely so i want to clear up my understanding:
declaration:
declares an entitys name and type to the compiler so it can be referenced before it is fully described, it doesnt allocate memory or provide body code.
extern int score;      	 variable declaration (no memory allocated yet)
void displayScore();     function declaration / prototype
class Player;          	 forward class declaration
struct Player {
    int health; 		 member declaration (allocated when a Player object is created)
};
definition:
provides the full specification of an variable / entity, causing the compiler or linker to allocate memory for variables or layout structures. every definition counts as a declaration.
int score = 100;          variable definition (allocates memory and initializes)
int health; 			  global definition (allocated and automatically initialized to 0)
struct Player {           type definition (defines memory layout for Player)
    std::string name;
    int level;
};
void takeDamage() {
    int health; 		  local definition (allocated, but value is garbage until assigned)
}
its easy to assume that 'int health' for eg is just a decleration, since no value is provided, but without the extern keyword or an explicit initializer is a definition,
the compiler reserves memory for health and zero-initialises it.
when defining a variable without a value, for eg with our 'int health' int example, the compiler always reserves memory for it without extern or an explicit initializer,
but how that memory is handled depends on where you declare it:
global / namespace scope: memory is allocated and automatically zero-initialized (health == 0).
int health; 			  // global definition: allocated and initialized to 0.
local scope (inside a function): memory is allocated on the stack, but it remains uninitialized, it holds an indeterminate "garbage" value.
void takeDamage() {
    int health; 		  // local definition: allocated, but value is garbage until assigned.
}
class / struct scope: declares a member variable inside the type definition. memory for health is allocated whenever an object of that class/struct is instantiated.
struct Player {
    int health; 		  // member declaration (allocated when a Player object is created).
};
